# Social Media Screentime & Wellbeing — NTI ML Internship Project

Your three responsibilities (Ensemble Learning, Unsupervised Learning, Deployment with UI)
built around the actual `social_media_screentime_mental_health_2026.csv` dataset (7,000 rows).

**Read `STUDY_GUIDE.md` before your discussion** — it has the plain-language explanations,
the presentation script, and 25+ defense questions with model answers. This README is the
technical run-book.

## The one thing to understand before anything else

`wellbeing_band` (the target) is a **deterministic formula** of `anxiety_score_0to27` and
`low_mood_score_0to27` — a depth-3 decision tree using only those two columns gets 100%
test accuracy (see `src/01_eda.py`, section 9). Both columns are excluded from every model
in this project, for two different reasons:
- **Supervised models**: including them would be target leakage — the model would decode
  the label formula instead of learning anything about behavior and wellbeing.
- **Clustering**: including them would make clusters trivially mirror the 3 existing bands,
  defeating the point of unsupervised discovery.

Everything else in this project is designed around that one finding.

│   └── wellbeing_pipeline.joblib    # created by 04_train_final_pipeline.py — this is what app.py loads (~30 MB, commit as-is)

**Why this structure and nothing fancier**: `config.py` + `preprocessing.py` are shared by
every other file, so there is exactly one definition of "which columns are features" and one
definition of "how they're transformed" in the whole project — training scripts and the
deployed app cannot silently drift apart. Numbered scripts (`01_`, `02_`, ...) run in the
order the assignment is structured, so you can `cd src && python 01_eda.py` straight down the
list. No `notebooks/` folder — everything here is a script specifically so it can be verified
to run end-to-end without hidden cell-execution-order bugs (see Part 22 below); you can still
open any of them in VS Code / Jupyter interactive mode using `# %%`-style cell breaks if you
prefer a notebook feel.

## Exact commands to reproduce everything from a fresh environment

```bash
# 1. Get the code + data into one folder (adjust if you're not using git)
cd nti_wellbeing_project

# 2. Create an isolated environment (avoids version conflicts with anything else on your machine)
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

# 3. Install exact dependencies
pip install -r requirements.txt

# 4. Run the analysis, in order (each writes plots/CSVs into outputs/)
cd src
python 01_eda.py
python 02_ensemble_learning.py
python 03_unsupervised_learning.py
python 04_train_final_pipeline.py     # creates ../models/wellbeing_pipeline.joblib

# 5. Run the app (from the PROJECT ROOT, not src/)
cd ..
streamlit run app.py
```

Streamlit will print a local URL (typically `http://localhost:8501`) — open it in a browser.
Fill in the form and click **Predict my wellbeing band**.

## Reproducibility: why `random_state=42` is everywhere

`random_state=42` (defined once, in `src/config.py`) is passed to every train/test split,
every bootstrap-based model (Bagging, Random Forest, AdaBoost), and every K-Means fit in this
project. Without a fixed seed, "random" operations like bootstrap sampling or centroid
initialization would give a slightly different result every run — your reported metrics
wouldn't match what your teammates get re-running the same code, and you couldn't
double-check your own numbers later. `42` specifically has no mathematical significance;
it's a widely-used convention (a nod to *The Hitchhiker's Guide to the Galaxy*) — any fixed
integer works identically, what matters is that it's fixed and consistent everywhere.

## Deploying online (Streamlit Community Cloud)

This is the simplest option for an NTI-scale project — free, and it deploys straight from a
GitHub repo with no server management. A few things below matter more than they look, so
read this section fully rather than skimming — most Streamlit Cloud deploy failures trace
back to one of these.

### Why `requirements.txt` uses exact pins (`==`), not `>=`

scikit-learn does **not** guarantee that a model pickled (via `joblib`) with one version will
load correctly with a different version — a mismatch can throw warnings, errors, or in the
worst case silently misbehave. `requirements.txt` pins `scikit-learn==1.8.0`, `numpy==2.4.4`,
etc. to the exact versions that trained and saved `models/wellbeing_pipeline.joblib`, so
Streamlit Cloud installs the identical library versions rather than pip resolving to whatever
is newest at deploy time. **Verified**: these exact pins were tested by installing into a
completely empty virtual environment from scratch and confirming the saved pipeline loads and
predicts with no version warnings — see the commands above under "Exact commands to
reproduce everything," which you can rerun yourself to double-check.

If you ever retrain the model, update these pins to match and commit the new `.joblib` and
the updated `requirements.txt` **in the same commit** — they must always travel together.

### A current Streamlit Cloud platform quirk to know about

As of mid-2026, there are open, active bug reports of Streamlit Community Cloud occasionally
ignoring both `runtime.txt` and the "Python version" dropdown in Advanced Settings, silently
building with a newer Python than requested. This project doesn't use `runtime.txt` at all
(it's unreliable right now — don't add one). Streamlit Cloud's documented **default is
Python 3.12**, which is exactly what this project was built and tested with, so in the normal
case you don't need to touch anything. Still, explicitly select **3.12** from the "Python
version" dropdown in Advanced Settings when you deploy (step 3 below) rather than leaving it
on whatever the default happens to be — it costs nothing and matches what was tested.

**If deployment still fails or the app errors on startup**: check the deployment logs for a
line like `Using Python 3.13...` or `3.14...` — if the platform silently used a different
Python version than requested, that's this known issue, not a mistake in your code. The fix:
delete the app and redeploy (Python version can only be set at deploy time, not changed
afterward), re-confirming 3.12 in Advanced Settings. This is a platform-side issue that comes
and goes, not something fixable from your repo.

### Steps

1. **Push this folder to a GitHub repository.** Required structure for Streamlit Cloud to
   find everything: `app.py` at the repo root, `requirements.txt` at the repo root, and
   `models/wellbeing_pipeline.joblib` committed to the repo (Streamlit Cloud has no separate
   persistent storage — the model file must be inside the repo it deploys from).
   ```bash
   git init
   git add .
   git commit -m "NTI wellbeing prediction project"
   git branch -M main
   git remote add origin <your-repo-url>
   git push -u origin main
   ```
   `wellbeing_pipeline.joblib` is ~30 MB — comfortably under GitHub's 100 MB per-file hard
   limit, so it commits normally with plain `git add`, no Git LFS needed. The `.gitignore` in
   this project deliberately does **not** exclude `models/` or `outputs/` — only local
   environment cruft (`venv/`, `__pycache__/`) is excluded, since the model file specifically
   needs to be committed for the app to work at all.
2. Go to **share.streamlit.io**, sign in with GitHub, click **New app**.
3. Select your repository, branch `main`, and set the main file path to `app.py`. Click
   **Advanced settings** and explicitly select **Python 3.12** (see quirk note above) before
   deploying.
4. Click **Deploy**. Streamlit Cloud installs `requirements.txt` automatically (using the
   exact pinned versions) and runs `streamlit run app.py` for you.
5. **How the deployed app finds the model file**: `app.py` builds its path with
   `os.path.join(os.path.dirname(__file__), "models", "wellbeing_pipeline.joblib")` — a path
   relative to `app.py`'s own location, not your local machine's absolute path. As long as the
   `models/` folder is committed to the repo at the same level as `app.py`, this resolves
   correctly both locally and on Streamlit Cloud with zero changes.

### Resource limits (free tier) and whether this app fits

Streamlit Community Cloud's free tier gives each app roughly **1 GB of RAM** and puts apps to
sleep after about 12 hours with no visitors (the next visitor sees a brief "waking up" screen
— worth knowing so it doesn't look broken if you open it right before your discussion after
it's sat idle). Loading `wellbeing_pipeline.joblib` was measured at **~215 MB of RAM** in this
build — comfortable headroom under the 1 GB limit even accounting for Streamlit's own
baseline memory use. `app.py` also wraps model loading in `@st.cache_resource`, which loads
the pipeline into memory **once per app instance and shares it across all users**, rather than
reloading it per visitor session — this is the main thing keeping memory use flat regardless
of how many people try the app during your discussion. If you ever do hit resource limits
(e.g. after adding more features later), the first thing to try is reducing
`n_estimators` in `04_train_final_pipeline.py` and resaving — fewer trees means a smaller,
lighter pipeline.

If you'd rather not deploy publicly, running it locally with `streamlit run app.py` and
sharing your screen is entirely sufficient for an internship discussion — deployment platform
choice doesn't change anything about the ML content itself.
